# RA-35 — An evaluator cannot reach the dashboard without asking for a password

**Severity:** Medium · **Area:** `src/app/login/page.tsx` · **Est:** 1 h

## Summary
RA-05 put every page and every data route behind a dashboard session, which was right: `/api/customers` returns customer names, emails and phone numbers, and `/api/recovery/trigger` makes the system contact people.

It also means a judge who opens the hosted demo URL sees a login form and nothing else. The submission gives them a link; it does not give them credentials, and there is no mechanism by which they could obtain any. The deployment is therefore unusable by exactly the audience it exists for.

## Impact
RA-28 argued that a live URL *"materially raises the chance the project is actually examined"*. A live URL that cannot be entered raises nothing. This is the difference between a judge spending five minutes in the dashboard and a judge closing the tab.

## Proposed fix
A **"Sign in as evaluator"** button on the login page that signs in with published credentials.

Publishing a password is normally indefensible, so the conditions that make it defensible here have to be enforced rather than assumed:

1. **Gate it.** Render the button only behind an explicit flag (`NEXT_PUBLIC_DEMO_LOGIN`). A deployment holding real customer records leaves it unset and the button does not exist — publishing a password beside real PII would undo RA-05 entirely.
2. **Say what is behind it.** The copy states that every record is synthetic, generated by `src/lib/db/seed.ts`. That fact is what the decision rests on, so it belongs on screen rather than in a reviewer's head.
3. **Do not bypass anything.** The button posts to `/api/auth/login` exactly as the form does, receives a normally signed session, and a wrong password is still refused. It is a filled-in form, not a back door.

## Acceptance criteria
- [ ] A judge with only the URL can reach the dashboard in one click
- [ ] The button is absent unless the demo flag is set
- [ ] The published credentials and the deployment's configured credentials cannot drift apart unnoticed
- [ ] The auth path itself is unchanged — wrong credentials still fail
